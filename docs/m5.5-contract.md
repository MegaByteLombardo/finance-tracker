# M5.5 contract — backend ↔ presentation

**Status:** frozen · **Milestone:** M5.5 — Currency Exchange Transactions

This document extends [m2-contract.md](m2-contract.md), [m3-contract.md](m3-contract.md),
[m4-contract.md](m4-contract.md) and [m5-contract.md](m5-contract.md), which
**remain in force except where this document contradicts them**. Everything they
froze — money as decimal strings, dates as `YYYY-MM-DD`, the optional-field
convention, `errors.Is` for error handling, balances derived from movements,
editing as replacement, exact decimal arithmetic — still holds.

M5.5 adds one transaction type. It changes nothing about exchange rates, nothing
about valuation, and nothing about the four types that came before it.

## The one rule, unchanged

**The presentation layer never writes SQL, never opens a transaction, never
imports a repository, and never performs financial arithmetic.**

There is one bounded exception in M5.5, stated so that it cannot spread: the
*implied rate preview* on the exchange form is computed in the browser with
ordinary JavaScript arithmetic. It is never stored, never posted, and never
compared with what the backend derives. What the ledger records is the two
amounts, and the rate that comes back is the exact one.

---

## 1. The rule that governs this milestone

```
Reference / Valuation FX        ≠        Execution FX
```

| | What it is | Where it lives |
| --- | --- | --- |
| **Reference FX** | What a *source* said one currency was worth on a day. Used to express balances the user already holds in one currency, for presentation. | `exchange_rates`, `internal/fx`, `internal/valuation`. All of M5. |
| **Execution FX** | The rate an operation the user *actually performed* happened at: 84,220.67 bolívares handed over for 100 dollars. | Nowhere, as a stored value. It is **derived** from the two amounts of an `FX_EXCHANGE`, on every read. |

M5 stated this rule and implemented only the first half, with "Transaction FX"
as the name for the half it did not build. **M5.5 builds a strictly narrower
thing than that name suggested**, and the difference is the whole point:

- An `FX_EXCHANGE` is an **operation between two accounts the user owns**. Money
  left one and arrived in the other. Both amounts are facts on a statement.
- **No transaction carries a rate.** `transactions` gained no `exchange_rate_id`,
  no `fx_rate`, no `transaction_rate`, and no column of any kind. The two
  movements state the rate exactly; a third copy could only ever disagree with
  them.
- **Recording an exchange reads no exchange rate and writes none.** The BCV is
  not consulted to decide how much money moved. `exchange_rates` is not touched,
  not created, not updated, not archived.
- What is still **not built**: FX attached to an ordinary income or expense, a
  merchant's rate, a card's rate, cost basis, realized or unrealized FX gains.

### Why the difference is worth the sentence

A reference rate answers *"what is this worth today?"*. An execution rate answers
*"what did I get for it on the 16th?"*. They are different questions about
different moments, and conflating them would make it impossible to say later
which one a stored number meant.

A consequence follows and is intended: **after an exchange at a rate other than
the reference rate, the valued net worth changes.** Buying dollars above the
official rate reduces it; buying below it raises it. That difference is **not**
converted into an expense, an income, a fee, a gain or a loss. There is no such
row and no code that would create one.

## 2. `FX_EXCHANGE`

```go
const FXExchange TransactionType = "FX_EXCHANGE"
```

```
Compra de USD                          Venta de USD

Banesco VES                            Mercantil USD
-85,000.00 VES                         -100.00 USD
        ↓                                      ↓
Mercantil USD                          Banesco VES
+100.00 USD                            +84,500.00 VES
```

**One transaction, two movements**, exactly as a `TRANSFER` — and nothing was
added to `transactions` for either of them. The two-table ledger was built for
this.

### It is not a `TRANSFER`

| | `TRANSFER` | `FX_EXCHANGE` |
| --- | --- | --- |
| currencies | the two accounts **must share** one | the two accounts **must differ** |
| amounts | one | two, one per currency |
| the two movements | equal and opposite, summing to zero | opposite in sign, **unrelated in magnitude** |
| total held in the currency | unchanged, always | changes, in both currencies |

**`TRANSFER` was not widened to accept two currencies**, and must not be. They
are different financial events: one moves a sum of money, the other exchanges one
sum for another. `ErrCurrencyMismatch` and `ErrSameCurrency` are mirror images of
each other and each belongs to exactly one of them.

**Nothing compares the two magnitudes.** `abs(source) == destination` is not a
rule here and never will be: 8,500,000 céntimos is not 10,000 cents, and asserting
a relation between them would be asserting something about two different kinds of
quantity.

### It is not income and not an expense

Nothing was earned and nothing was consumed; the same wealth is denominated
differently afterwards. So:

```
category_id       = NULL
payment_method_id = NULL
```

enforced by the table `CHECK`, not only by the service. A commission charged on
top is a **separate `EXPENSE`** under a category such as "Bank fees". If the user
only knows the two final amounts, those are exactly what to enter — the derived
execution rate then already reflects what the commission cost.

### There is no BUY and no SELL

There is no `BUY_USD` and no `SELL_USD`, and there must not be: they would be two
names for one event, distinguished by a fact the movements already state.

**Which currency was bought is which one was the destination.** "Compra de USD"
and "Venta de USD" are labels a screen infers; the ledger stores one type.

## 3. Invariants

A recorded exchange satisfies all of these, and a stored one is refused on read
if it does not:

```
source_account      ≠  destination_account
source_currency     ≠  destination_currency

source_amount       >  0    (as input)
destination_amount  >  0    (as input)

source movement      = -source_amount        in the source currency's minor units
destination movement = +destination_amount   in the destination currency's minor units

category_id       IS NULL
payment_method_id IS NULL
```

Both accounts must exist and be **active**, the same rule a transfer applies.

**There is no insufficient-funds rule**, for exactly the reasons recorded in
TD-043: the ledger records what happened, overdrafts happen, and `effective_date`
can be backdated so a check at the moment of writing would only sometimes apply.

Each amount is read at **its own account's currency scale**. There is no shared
scale and there must not be one: reading a bolívar amount at a dollar's scale
would be the quietest possible way to be wrong.

All of it is written in **one `sql.Tx`**. If anything fails, everything rolls
back. There is never an exchange that removed bolívares and produced no dollars.

## 4. The derived execution rate

```
84,220.67 VES   for   100.00 USD      →      1 USD = 842.2067 VES
85,000.00 VES   for   100.00 USD      →      1 USD = 850 VES
```

**It is derived, never stored.** It is recomputed from the two amounts on every
read, with `math/big` — exact rational arithmetic, no `float32`, no `float64`, no
SQLite `REAL` anywhere on the path, and the source-parsing test that has enforced
that since M5 covers `internal/ledger`.

```go
type ExecutionRate struct {
    BaseCurrencyCode  string
    QuoteCurrencyCode string
    Rate              money.Decimal  // domain only
    RateFormatted     string         // what crosses the boundary
    Exact             bool
}
```

`money.Decimal` stops at the adapter. The presentation layer receives
`RateFormatted` and `Exact`, because it displays a rate and never computes with
one.

### Scale

The rate carries the **smallest scale that states it exactly**: `"850"` rather
than `"850.000000000000"`, `"842.2067"` rather than `"842.20670000"`.

A rate with no finite decimal expansion — 100 VES for 3 USD — is rounded **half
to even** at `money.MaxScale` (12) places and `Exact` is **false**. An interface
showing one must say so; both the desktop and the mobile views prefix it with
`≈`. An approximation is never presented as a fact.

### Orientation

The project's, unchanged:

```
1 BaseCurrencyCode  =  Rate  QuoteCurrencyCode
```

Which of the two currencies is the base is decided by **one rule, applied in
order**:

1. **If exactly one side is USD, USD is the base.** `1 USD = 842.2067 VES` is how
   the rate was quoted to the user, whichever direction they traded in — so a
   purchase and a sale of the same pair can be compared at a glance.
2. **Otherwise the base is whichever side makes the rate at least 1**, so a pair
   reads in units of the cheaper currency: `1 EUR = 990 VES`, never
   `1 VES = 0.00101 EUR`.
3. **An exact tie is broken by the destination.** It exists so that the answer is
   always the same one.

The base is therefore **not always the destination**. The choice is made in the
domain, not in a template, because it requires comparing two exact fractions.

**A template must never reverse a rate by relabelling it.** The inverse is a
different number, not the same string with the codes swapped — the same rule
M5 froze for reference rates.

## 5. Use cases

```go
RecordExchange(ctx, RecordExchangeInput) (TransactionView, error)
UpdateExchange(ctx, id, UpdateExchangeInput) (TransactionView, error)
```

```go
type RecordExchangeInput struct {
    SourceAccountID      int64
    SourceAmount         string   // positive decimal, at the source currency's scale
    DestinationAccountID int64
    DestinationAmount    string   // positive decimal, at the destination currency's scale
    Description          *string  // nil for none; "" is a caller mistake
    EffectiveDate        string   // "YYYY-MM-DD", required
}
```

`UpdateExchangeInput` is the same six fields. Both amounts are **positive**: the
direction is which account was named as the source, never a sign.

**There is no rate field, and there must never be one.** Supplying a rate and one
amount would make the application compute the other, and the computed one would
disagree with the bank by a céntimo whenever the bank rounded differently. M5.5
deliberately does not offer that mode.

### Editing

Everything can be corrected: both accounts, both amounts, the date, the
description. Swapping the two accounts turns a purchase into a sale.

**The two movements keep their ids** (TD-042). An edit corrects an event; it does
not replace it with a different one, and nothing in this application deletes a
financial row.

**`UpdateExchangeInput` has no `AllowCurrencyChange`**, and its absence is
deliberate. That flag exists on the transfer and transaction edits because those
carry **one** amount, so moving them to another currency re-reads the same digits
at another scale and silently means a different sum of money. An exchange names
both currencies explicitly, one amount for each, each read at its own account's
scale. There is no reinterpretation to confirm.

### Type guards

**Each type has its own edit use case, and every guard names what it ACCEPTS**
(TD-045):

| Use case | Accepts |
| --- | --- |
| `UpdateTransaction` | `INCOME`, `EXPENSE` |
| `UpdateOpeningBalance` | `OPENING_BALANCE` |
| `UpdateTransfer` | `TRANSFER` |
| `UpdateExchange` | `FX_EXCHANGE` |

Everything else is `ErrTypeChangeNotAllowed`. None of these conversions is
possible in either direction:

```
FX_EXCHANGE  ↔  INCOME | EXPENSE | OPENING_BALANCE | TRANSFER
```

The same rule holds at the **presentation layer**, where M5.5 rewrote two guards
that had been written as exclusions. `GET /transactions/{id}/edit` and
`POST /transactions/{id}` now `switch` over every type and refuse the default —
so a sixth type added later is rejected rather than silently filed as an expense.

## 6. The read model

```go
type ExchangeDetail struct {
    SourceMovementID     int64
    SourceAccountID      int64
    SourceAccountName    string
    SourceCurrencyCode   string
    SourceCurrencySymbol *string
    SourceMinorUnit      int
    SourceAmountMinor    int64   // POSITIVE: the amount delivered
    SourceAmountFormatted string

    DestinationMovementID     int64
    DestinationAccountID      int64
    DestinationAccountName    string
    DestinationCurrencyCode   string
    DestinationCurrencySymbol *string
    DestinationMinorUnit      int
    DestinationAmountMinor    int64   // POSITIVE: the amount received
    DestinationAmountFormatted string

    ExecutionRate ExecutionRate
}
```

`TransactionView.Exchange` is set **if and only if** `Type` is `FX_EXCHANGE`, and
that nil is how a template knows a row is not one.

**For an exchange this is the only field that should be read.** The reason is
stronger than it is for a transfer: `TransactionView` is one row per transaction,
anchored on the source movement, so `CurrencyCode`, `MinorUnit` and
`AmountFormatted` all describe **the currency the money left**. A caller reading
them would render `-85,000.00 VES` with no way to discover that `100.00 USD`
arrived.

Both amounts are **positive** in the detail; the stored movements hold the signs.

### A malformed exchange is an integrity failure

Reading one returns `ErrInconsistentExchange` — a `500`, not a message on a form.
No input can produce one, so reaching it means the database was modified by
something else. The conditions refused:

- not exactly two movements
- both movements positive, or both negative
- both movements in the same account
- both movements in the **same currency** (that is the shape of a transfer)

It is **reported, never rendered half-way**, and never silently skipped: the
listing anchors structurally, on `min(movement_id)`, precisely so that a broken
row complains instead of disappearing (TD-044).

## 7. Errors

| Error | Meaning | Suggested status |
| --- | --- | --- |
| `ErrNotFound` | no such transaction | 404 |
| `ErrSameAccount` | source and destination are the same account | 422 |
| `ErrSameCurrency` | the two accounts are in the **same** currency — that is a transfer | 422 |
| `ErrInvalidAmount` | an amount is missing, unparseable, not positive, or has too many decimals for its currency | 422 |
| `ErrInvalidInput` | bad date, blank description | 422 |
| `ErrAccountNotFound` / `ErrAccountInactive` | wrapped in `AccountSideError`, which names the side | 422 |
| `ErrTypeChangeNotAllowed` | this transaction is not an exchange, or an exchange was sent to another use case | 400/422 |
| `ErrInconsistentExchange` | the stored exchange is malformed | **500** |

### `AccountSideError`

M4 introduced `TransferAccountError` and `TransferSide` for a form with two
account fields. An exchange form has two as well, so M5.5 renames them to
`AccountSideError` and `MovementSide` — and keeps the M4 names as **type
aliases**, not as parallel types:

```go
type MovementSide string
type TransferSide = MovementSide            // the same type

type AccountSideError struct{ Side MovementSide; AccountID int64; Err error }
type TransferAccountError = AccountSideError // the same type
```

`errors.As` with either spelling matches the same value, so every M4 call site
keeps working unchanged and nothing has to convert between two vocabularies.

## 8. Valuation is untouched

**No special net-worth logic was added, and none may be.**

Balances change through movements, as they always have: bolívares down, dollars
up. `internal/valuation` then values those balances with the **reference** rates,
exactly as it did in M5. The execution rate of an `FX_EXCHANGE` takes **no part**
in `ValuationService` — it is not read, not resolved, not compared.

The net worth remains **derived on every read and never stored** (TD-052).

## 9. The interface

### Desktop

| Route | Purpose |
| --- | --- |
| `GET /exchanges/new` | the form |
| `POST /exchanges` | record |
| `GET /exchanges/{id}/edit` | the edit form |
| `POST /exchanges/{id}` | correct |

Fields: **cuenta origen · monto entregado · cuenta destino · monto recibido ·
fecha · descripción**. Choosing the source restricts the destination to accounts
in a **different** currency — a hint, not the rule; the backend refuses the same
combinations whatever the browser did.

The implied rate is previewed while typing. **The backend remains the authority.**

In the listing an exchange shows both amounts, both codes, the two accounts and
the derived rate:

```
Compra USD          Banesco VES → Mercantil USD
                    -84,220.67 VES
                    +100.00 USD
                    1 USD = 842.2067 VES
```

### Mobile

The "Nueva operación" sheet offers a fourth entry, **Cambiar divisas**, and the
operation form a fourth tab, **Cambio**, with a second amount field and the same
implied-rate preview.

M5.5 also fixed a latent bug in that form. It posts to four endpoints with four
sets of field names, and until now the template hard-coded the income shape while
a script rewrote it on the first tab click — so opening
`/mobile/operacion/nueva?type=TRANSFER` directly gave a form that would have
posted a transfer to `/transactions`. **The server now renders the shape it was
asked for**, and the script keeps it in step from there. A test reads
`mobile.js` and checks its table against the Go one, so the two cannot drift.

## 10. Schema

**Migration `00013`, schema version 13.** One change: the `transaction_type`
`CHECK` admits `FX_EXCHANGE`, and the shape `CHECK` requires it to carry no
category and no payment method.

**No table was added. No column was added anywhere.** In particular
`transactions` gained no rate column, and `account_movements` gained no currency
column — a movement is denominated in its account's currency by construction, and
an exchange needs no new column to say its two accounts differ.

SQLite cannot alter a `CHECK`, so the table is rebuilt, following **TD-037**
exactly as `00009` and `00010` did: the **child** `account_movements` is rebuilt
and dropped **first**, then the parent, then both are renamed into place and the
five indexes recreated. `foreign_keys` stays `ON` throughout.

It is **forward-only** (TD-038). There is no honest way back: an exchange cannot
become a transfer, because its accounts are in different currencies; it cannot
become an income plus an expense without inventing a category for each; and
discarding it would destroy the record of money that actually changed hands. The
way back is the pre-migration snapshot, which is taken automatically and was
verified to still work.

## 11. Out of scope, and not to be added opportunistically

- an FX fee or commission model
- an exchange-rate column on `transactions`, in any spelling
- cross-currency `TRANSFER`
- FX gains and losses, realized or unrealized
- cost basis, lot tracking, tax accounting
- a rate-driven input mode (enter a rate, let the application compute the other
  amount)
- automatic or scheduled exchanges
- historical FX performance
- new rate providers, browser automation of any kind
- **any delete**, and any history of edited records — the undo is a backup
